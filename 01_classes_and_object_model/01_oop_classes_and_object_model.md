# Часть I. От данных к классу

## 4. Разрозненные переменные

Допустим, программа хранит состояние игрока:

~~~cpp
const char* playerName = "Alex";
int playerHealth = 100;
int playerX = 0;
int playerY = 0;
bool playerAlive = true;
~~~

Все переменные относятся к одной сущности, но язык пока никак не выражает эту связь. Для второго игрока придётся создавать ещё один набор имён. Функция легко может получить здоровье одного игрока и координату другого.

Первая версия: [01_related_variables.cpp](steps/01_related_variables.cpp).

## 5. Структура как пользовательский тип

Структура объединяет связанные данные:

~~~cpp
struct Player {
    const char* name;
    int health;
    int x;
    int y;
    bool alive;
};
~~~

Теперь <code>Player</code> — тип, а <code>first</code> и <code>second</code> — разные объекты этого типа:

~~~cpp
Player first{"Alex", 100, 0, 0, true};
Player second{"Sam", 80, 5, 2, true};
~~~

Доступ к члену объекта выполняется оператором `.`:

~~~cpp
first.health = 90;
second.x = 6;
~~~

### Термины

- **класс** или **структура** — объявленный пользователем тип;
- **объект** — конкретный экземпляр типа;
- **поле** — данные, входящие в объект;
- **состояние** — совокупность текущих значений полей.

Следующий шаг: [02_player_struct.cpp](steps/02_player_struct.cpp).

## 6. Что означает const char*

В первых примерах имя хранится как <code>const char*</code>:

~~~cpp
const char* name = "Alex";
~~~

Здесь:

- <code>char</code> — тип одного символа;
- <code>char*</code> — указатель на первый символ последовательности;
- <code>const</code> запрещает изменять символы через этот указатель;
- завершающий символ <code>'\0'</code> обозначает конец C-строки, явно указывать его не нужно, он будет выставлен компилятором неявно.

Такое поле **не владеет** символами и не копирует их. В этой работе имена задаются строковыми литералами, которые живут до завершения программы.

> [!warning] Сравнение C-строк
> Выражение <code>firstName == secondName</code> сравнивает адреса, а не текст. Для сравнения содержимого используется <code>std::strcmp</code> из <code>&lt;cstring&gt;</code>.

~~~cpp
#include <cstring>

if (std::strcmp(firstName, secondName) == 0) {
    // Тексты совпадают.
}
~~~

В последующих работах для переменных, владеющих содержимым строк будет использоваться <code>std::string</code>.

## 7. Методы связывают данные с поведением

Функцию, объявленную внутри класса, называют методом:

~~~cpp
struct Player {
    const char* name = "Unknown";
    int health = 100;
    bool alive = true;

    void takeDamage(int amount) {
        if (amount <= 0 || !alive) {
            return;
        }

        if (amount >= health) {
            health = 0;
            alive = false;
        } else {
            health -= amount;
        }
    }
};
~~~

Вызов метода:

~~~cpp
Player player;
player.takeDamage(30);
~~~

Метод вызывается для конкретного объекта класса и работает с его полями. Код находится в [03_player_methods.cpp](steps/03_player_methods.cpp).

### Упражнение 1

Добавьте метод <code>heal(int amount)</code>. Требования:

- отрицательное значение игнорируется;
- здоровье не превышает 100;
- погибшего игрока нельзя лечить;
- сложение не должно выполняться до проверки верхней границы.

## 8. Struct и class

В C++ обе конструкции могут содержать поля, методы, конструкторы и вложенные типы. Основные языковые различия — доступ по умолчанию:

| Конструкция | Доступ к членам по умолчанию | Наследование по умолчанию |
|---|---|---|
| <code>struct</code> | <code>public</code> | <code>public</code> |
| <code>class</code> | <code>private</code> | <code>private</code> |
Про наследование будем говорить подробнее на следующих занятиях.

~~~cpp
struct OpenData {
    int value;       // public
};

class ProtectedData {
    int value;       // private
};
~~~

Практическое соглашение:

- <code>struct</code> — простой открытый набор связанных значений;
- <code>class</code> — тип с защищённым состоянием и поведенческим интерфейсом.

Это соглашение, а не дополнительное правило языка.

## 9. Инкапсуляция и инварианты

Открытое поле можно испортить в любой части программы:

~~~cpp
player.health = -500;
~~~

Хорошо спроектированный класс скрывает состояние и предоставляет операции для корректного изменения состояния:

~~~cpp
class Player {
public:
    void takeDamage(int amount);
    void heal(int amount);
    int getHealth() const;
    bool isAlive() const;

private:
    int health = 100;
    bool alive = true;
};
~~~

**Инвариант** — условие, истинное для любого корректного наблюдаемого состояния объекта. Для игрока:

~~~text
0 <= health <= 100
alive == (health > 0)
~~~

Инкапсуляция нужна не просто для сокрытия полей. Её цель — сосредоточить правила изменения состояния внутри самого типа.

Готовый этап: [04_player_class_invariants.cpp](steps/04_player_class_invariants.cpp).

# Часть II. Конструкторы и Robot v1

## 10. Проблема начального состояния

Объект должен стать корректным сразу после создания. Если пользователь обязан вызвать несколько методов после объявления объекта, он может забыть один из шагов.

Конструктор выполняется автоматически при создании объекта:

~~~cpp
class Robot {
public:
    Robot() {
        // Начальная настройка объекта.
    }
};
~~~

У конструктора:

- имя совпадает с именем класса;
- нет возвращаемого типа;
- может быть список параметров;
- может быть несколько перегруженных вариантов.

## 11. Конструктор по умолчанию

Конструктор по умолчанию можно вызвать без аргументов:

~~~cpp
class Robot {
public:
    Robot() {
    }
};

Robot robot;
~~~

Если начальные значения уже заданы у полей, компиляторную реализацию можно запросить через <code>= default</code>:

~~~cpp
class Robot {
public:
    Robot() = default;

private:
    const char* name = "Unknown";
    int energy = 100;
    int x = 0;
    int y = 0;
};
~~~

Пример: [05_default_constructor.cpp](steps/05_default_constructor.cpp).

## 12. Параметризованный конструктор

Параметризованный конструктор получает данные от вызывающего кода:

~~~cpp
Robot(const char* robotName, int initialEnergy)
    : name(robotName), energy(initialEnergy) {
}
~~~

Часть после двоеточия называется **списком инициализации**. Поля создаются сразу с нужными значениями.

~~~cpp
Robot first("R2D2", 80);
Robot second("C3PO", 60);
~~~

Используйте список инициализации вместо присваивания уже созданным полям в теле конструктора.

Пример: [06_parameterized_constructor.cpp](steps/06_parameterized_constructor.cpp).

## 13. Порядок инициализации полей

Поля инициализируются в порядке объявления в классе, а не в порядке записи после двоеточия:

~~~cpp
class Battery {
private:
    int capacity;
    int charge;

public:
    explicit Battery(int maximum)
        : capacity(maximum), charge(capacity) {
    }
};
~~~

Практическое правило: записывайте элементы списка инициализации в том же порядке, в котором поля объявлены.

## 14. Перегрузка и делегирование конструкторов

Один класс может поддерживать несколько способов создания:

~~~cpp
class Robot {
public:
    Robot()
        : Robot("Unknown", 100) {
    }

    explicit Robot(const char* robotName)
        : Robot(robotName, 100) {
    }

    Robot(const char* robotName, int initialEnergy)
        : name(robotName), energy(normalize(initialEnergy)) {
    }
};
~~~

Первые два конструктора **делегируют** работу третьему. Общая проверка не дублируется.

Делегирование выполняется в списке инициализации, а не вызовом временного объекта в теле конструктора.

## 15. Explicit и преобразующие конструкторы

Конструктор с одним аргументом может участвовать в неявном преобразовании:

~~~cpp
class Robot {
public:
    Robot(const char* name);
};
~~~

Чтобы создание объекта оставалось явным, используется <code>explicit</code>:

~~~cpp
explicit Robot(const char* name);

Robot first("R2D2");       // Разрешено.
// Robot second = "C3PO";  // Неявное преобразование из const char* в Robot запрещено explicit.
~~~

Полный пример перегрузки, делегирования и <code>explicit</code>: [07_delegating_explicit.cpp](steps/07_delegating_explicit.cpp).

## 16. Default, deleted, copy и move: карта конструкторов

| Вид | Пример | Назначение |
|---|---|---|
| По умолчанию | <code>Robot()</code> | Создание без аргументов |
| Параметризованный | <code>Robot(const char*, int)</code> | Создание из входных данных |
| Делегирующий | <code>Robot() : Robot(...) {}</code> | Передача работы другому конструктору того же класса |
| Преобразующий | <code>Robot(int)</code> | Может преобразовать один тип в объект класса |
| Явный | <code>explicit Robot(int)</code> | Запрещает нежелательное неявное преобразование |
| Сгенерированный | <code>Robot() = default</code> | Явно запросить стандартную реализацию |
| Запрещённый | <code>Robot() = delete</code> | Запретить способ создания |
| Копирующий | <code>Robot(const Robot&amp;)</code> | Создать объект как копию |
| Перемещающий | <code>Robot(Robot&amp;&amp;)</code> | Создать объект с переносом ресурсов |

Копирующий и перемещающий конструкторы относятся к специальным функциям класса. Их ручная реализация будет рассматриваться на дальнейших занятиях. На текущем этапе классы состоят из простых полей, поэтому подходят автоматически сгенерированные операции.

Если корректного состояния без аргументов не существует, конструктор можно запретить:

~~~cpp
class Temperature {
public:
    Temperature() = delete;
    explicit Temperature(double value);
};
~~~

## 17. Проект Robot v1

### Инварианты

~~~text

0 <= energy <= 100
active == false запрещает движение
успешное движение изменяет ровно одну координату на единицу
неуспешное движение не изменяет координаты и энергию
~~~

### Интерфейс

~~~cpp
class Robot {
public:
    Robot();

    Robot(const char* robotName, int initialEnergy);

    bool moveRight();

    int getY() const;

    void printStatus() const;

    const char* name;
    int energy;
    int x;
    int y;
    bool active;

    bool spendMovementEnergy();
    static int normalizeEnergy(int value);
};
~~~

# Часть III. Жизненный цикл и константность

## 18. Жизненный цикл объекта

~~~text
Память для объекта
        ↓
Инициализация базовых частей и полей
        ↓
Тело конструктора
        ↓
Работа с объектом
        ↓
Деструктор
        ↓
Завершение времени жизни
~~~

Локальный объект уничтожается при выходе из своей области видимости. Объекты во вложенной области уничтожаются раньше объектов внешней области.

~~~cpp
{
    Robot first("First");
    {
        Robot second("Second");
    } // second уничтожается здесь
}     // first уничтожается здесь
~~~

Деструктор:

~~~cpp
~Robot() {
    // Завершающие действия.
}
~~~

Деструктор задает правила по освобождению ресурсов объекта нашего класса в момент его уничтожения. У деструктора нет возвращаемого типа и параметров. У класса может быть только один деструктор. В текущем классе нет ручного ресурса, поэтому собственный деструктор не нужен; диагностический вывод используется только для наблюдения порядка.

Эксперимент: [09_lifecycle_destructor.cpp](steps/09_lifecycle_destructor.cpp).

## 19. Const-объекты и const-методы

Метод с <code>const</code> после параметров обещает не менять логическое состояние:

~~~cpp
int getEnergy() const {
    return energy;
}
~~~

У константного объекта доступны только константные методы:

~~~cpp
const Robot robot("Observer");
robot.getEnergy();  // Допустимо.
// robot.charge(10); // Ошибка компиляции.
~~~

Метод вывода обычно тоже должен быть <code>const</code>, если сам объект не изменяется.
Тут сразу укажу - static поля менять можно. Неизменными для const объекта считаются именно те поля, которые ему принадлежат. Static же поля никакому конкретному объекту не принадлежат.

## 20. Логическая константность и mutable

Различают:

- **физическую константность** — обычные поля не изменяются через <code>const</code>-интерфейс, тут подразумевается полная побитовая неизменность объекта в памяти, например, const int - гарантированно не поменяет своего значения;
- **логическую константность** — предметное значение объекта не изменяется, то что будет наблюдать пользователь извне, состояние объекта, не меняется, однако какие-то вспомогательные внутренние поля, например, кэш - могут меняться.

Кэш результата относится к реализации, а не обязательно к предметному состоянию:

~~~cpp
class Sensor {
public:
    explicit Sensor(int value)
        : rawValue(value) {
    }

    int level() const {
        if (!cacheValid) {
            cachedLevel = normalize(rawValue);
            cacheValid = true;
        }
        return cachedLevel;
    }

private:
    int rawValue;
    mutable bool cacheValid = false;
    mutable int cachedLevel = 0;
};
~~~

<code>mutable</code> разрешает изменять конкретное нестатическое поле внутри <code>const</code>-метода. Оно не делает изменяемым весь объект.

### Инвалидация кэша

При изменении исходных данных кэш нужно пометить недостоверным:

~~~cpp
void setRawValue(int value) {
    rawValue = value;
    cacheValid = false;
}
~~~

Корректные применения <code>mutable</code>:

- кэш;
- диагностический счётчик;
- внутренний объект синхронизации.

Некорректное применение — скрыть настоящее предметное изменение:

~~~cpp
mutable int balance;
void withdraw(int amount) const; // Неверный контракт.
~~~

Баланс является наблюдаемым состоянием, поэтому <code>withdraw</code> не должен быть <code>const</code>.

> [!warning] Потоки
> <code>const</code> и <code>mutable</code> сами по себе не обеспечивают потокобезопасность. Одновременное изменение кэша из нескольких потоков требует синхронизации.

Полный эксперимент: [10_const_mutable_cache.cpp](steps/10_const_mutable_cache.cpp).

# Часть IV. Организация и проектирование класса

## 21. Объявление и определение метода

Объявление сообщает интерфейс:

~~~cpp
class Robot {
public:
    void charge(int amount);
    int getEnergy() const;

private:
    int energy = 100;
};
~~~

Тут были объявлены поля класса и контракт взаимодействия с ними через объявление его методов. При этом в объявление функции включаются: имя функции, типы принимаемых аргументов и тип возвращаемый из функции.
 
Определение вне класса использует оператор области видимости <code>::</code>:

~~~cpp
void Robot::charge(int amount) {
    // Реализация.
}

int Robot::getEnergy() const {
    return energy;
}
~~~

И по поводу различных ключевых слов, которые указываются для функций: тут есть правило, если этот модификатор явно меняет тип функции, контракт взаимодействия, поведение - указывается и для определения и для объявления функции.
Вот, например, const. Поскольку это ключевое слово явно указывает на то, как будет вести себя функция - не изменяет нестатические поля, значит, нужно const указать как для объявления функции, так и для определения.

А какие-нибудь static, virtual, override, final уже указывают только на роль функции в классе. Их достаточно будет указать только в объявлении. 

## 22. Разделение на файлы

Обычная структура проекта:

~~~text
project/
├── Robot.hpp
├── Robot.cpp
└── main.cpp
~~~

В заголовочном файле находится объявление класса:

~~~cpp
#pragma once

class Robot {
public:
    explicit Robot(const char* name);
    int getEnergy() const;
};
~~~

В <code>Robot.cpp</code> находятся определения:

~~~cpp
#include "Robot.hpp"

Robot::Robot(const char* name)
    : name(name) {
}
~~~

В <code>main.cpp</code> заголовок подключается для использования типа. Заголовок не следует подключать через <code>#include "Robot.cpp"</code>.

Файл [11_out_of_class_overloads.cpp](steps/11_out_of_class_overloads.cpp) сохраняет пример единым для удобства сравнения, но определения уже вынесены за тело класса.

## 23. Перегрузка обычных методов

Методы с одним именем могут отличаться параметрами:

~~~cpp
void charge();
void charge(int amount);
~~~

Перегрузка только по возвращаемому типу запрещена: компилятор должен выбрать функцию до использования результата.

## 24. Указатель this

Внутри нестатического метода <code>this</code> указывает на текущий объект:

~~~cpp
class Robot {
public:
    explicit Robot(const char* name)
        : name(name) {
    }

private:
    const char* name;
};
~~~

Явная форма выглядит так:

~~~cpp
this->name = name;
~~~

Список инициализации обычно делает различие понятным без явного <code>this</code>. Статический метод не связан с конкретным объектом и поэтому не имеет <code>this</code>.

## 25. Композиция

Большой класс полезно разделить по ответственности:

~~~cpp
struct Position {
    int x = 0;
    int y = 0;
};

class Battery {
public:
    explicit Battery(int charge = 100);
    bool spend(int amount);
    void charge(int amount);
    int level() const;

private:
    int chargeLevel = 100;
};

class Robot {
private:
    const char* name = "Unknown";
    Position position;
    Battery battery;
};
~~~

Это отношение **has-a**:

~~~text
Robot имеет Position
Robot имеет Battery
~~~

Составные части конструируются до тела конструктора внешнего объекта и уничтожаются после начала его деструктора в обратном порядке.

Проект после выделения ответственностей: [12_composition.cpp](steps/12_composition.cpp).

## 26. Публичный интерфейс

Хороший интерфейс выражает предметные операции:

~~~cpp
robot.move(Direction::left);
robot.charge(20);
robot.deactivate();
~~~

Набор универсальных сеттеров позволяет нарушать смысл модели:

~~~cpp
robot.setEnergy(-1000);
robot.setX(500);
~~~

Публичный метод должен сообщать, **что** умеет объект. Приватный вспомогательный метод описывает, **как** класс избегает дублирования реализации.

## 27. Enum class

Направление лучше представить отдельным типом:

~~~cpp
enum class Direction {
    left,
    right,
    up,
    down
};
~~~

В отличие от неименованных числовых кодов, <code>enum class</code>:

- ограничивает допустимые значения;
- не смешивается неявно с целыми числами;
- требует квалифицированной записи <code>Direction::left</code>;
- делает интерфейс самодокументируемым.

## 28. Статические члены

Обычное поле принадлежит каждому объекту. Статическое поле принадлежит классу в целом:

~~~cpp
class Robot {
public:
    static int getSuccessfulMoves();

private:
    static int successfulMoves;
};
~~~

Запись внутри класса объявляет статическое поле, но в этом варианте ещё не создаёт для него память. Поле необходимо определить ровно один раз, обычно в соответствующем <code>.cpp</code>:

~~~cpp
// Robot.cpp
#include "Robot.hpp"

int Robot::successfulMoves = 0;
~~~

В определении за пределами класса слово <code>static</code> не повторяется.

~~~text
static int successfulMoves;       // объявление внутри класса
int Robot::successfulMoves = 0;   // определение и инициализация в .cpp
~~~

Если определение отсутствует, обращение к полю обычно приводит к ошибке линковщика. Обычное определение нельзя помещать в заголовок, включённый в несколько <code>.cpp</code>: это создаст несколько определений одного объекта.

### Inline static в C++17

Начиная с C++17 объявление и определение можно совместить:

~~~cpp
class Robot {
private:
    inline static int successfulMoves = 0;
};
~~~

Такую запись можно оставить в заголовочном файле. Отдельное определение в <code>Robot.cpp</code> не требуется, а во всей программе существует одно общее поле.

### Static constexpr

Константа времени компиляции инициализируется внутри класса:

~~~cpp
class Robot {
private:
    static constexpr int movementCost = 10;
};
~~~

У <code>constexpr</code>-поля должен быть инициализатор. Начиная с C++17 статический <code>constexpr</code>-член неявно является <code>inline</code>, поэтому отдельная строка в <code>.cpp</code> не нужна.

Статический метод можно вызвать без объекта:

~~~cpp
int count = Robot::getSuccessfulMoves();
~~~

Он не имеет <code>this</code> и не может напрямую обращаться к нестатическим полям без конкретного объекта.

При этом <code>const</code>-метод может менять статическое поле: <code>const</code> ограничивает состояние текущего объекта, а статическое поле объекту не принадлежит.

~~~cpp
class Robot {
public:
    int energy() const {
        ++readCount;
        return energyLevel;
    }

private:
    int energyLevel = 100;
    inline static int readCount = 0;
};
~~~

Изменение общего счётчика должно быть частью осознанного контракта. В многопоточной программе для него потребуется синхронизация или подходящий атомарный тип.

Совместный пример: [13_enum_static.cpp](steps/13_enum_static.cpp).

# Часть V. Представление объекта в памяти

> [!note] Углублённая ветка
> Эту часть можно пройти сразу после проектирования класса или вернуться к ней после лабораторной №3. Она описывает физическое представление, но не требуется для понимания RAII.

## 29. Размер и выравнивание

Оператор <code>sizeof</code> возвращает размер типа или объекта в байтах. <code>alignof</code> возвращает требование выравнивания:

~~~cpp
std::cout << sizeof(Position) << '\n';
std::cout << alignof(Position) << '\n';
~~~

Размер класса обычно включает нестатические поля и padding. Код методов и статические поля не копируются в каждый объект.

Даже пустой класс имеет ненулевой размер, чтобы разные объекты могли иметь разные адреса.

## 30. Padding

Компилятор может добавлять неиспользуемые байты для правильного размещения полей:

~~~cpp
struct LayoutA {
    char flag;
    int value;
    char state;
};

struct LayoutB {
    int value;
    char flag;
    char state;
};
~~~

Внутренний padding находится между полями, хвостовой — после последнего поля. Хвостовое дополнение обеспечивает правильное выравнивание следующего элемента массива.

Для standard-layout структуры смещения можно исследовать через <code>offsetof</code>:

~~~cpp
std::cout << offsetof(LayoutA, value) << '\n';
~~~

Конкретные числа зависят от платформы и ABI. Не запоминайте их как универсальные.

Эксперимент: [14_layout_alignment.cpp](steps/14_layout_alignment.cpp).

### Упражнение 4

1. Предскажите <code>sizeof</code> и смещения полей двух структур.
2. Запустите программу.
3. Нарисуйте байты объекта с padding.
4. Поменяйте порядок полей.
5. Объясните результат, не формулируя универсальное правило по одной платформе.

## 31. Union

В структуре все поля существуют одновременно. В <code>union</code> члены используют одну общую область памяти:

~~~cpp
union Storage {
    int count;
    double temperature;
    char grade;
};
~~~

Размер объединения достаточен для самого большого члена с учётом выравнивания. Обычно в каждый момент времени корректно читать тот член, который был записан последним. Его называют **активным членом**.

~~~cpp
Storage value{};
value.count = 42;          // count активен
value.temperature = 21.5; // теперь temperature активен
~~~

Чтение неактивного члена в общем случае не является безопасным способом преобразования представления.

## 32. Tagged union

Сам <code>union</code> не запоминает активный член. Добавим тег:

~~~cpp
enum class MeasurementKind {
    count,
    temperature,
    grade
};

struct Measurement {
    MeasurementKind kind;
    Storage value;
};
~~~

Каждая операция записи должна одновременно обновлять значение и тег. Каждая операция чтения сначала проверяет тег.

Полный учебный пример: [15_tagged_union.cpp](steps/15_tagged_union.cpp).

> [!warning] Граница примера
> Учебный union содержит только простые типы. Для безопасной альтернативы со сложными типами стандартная библиотека предоставляет <code>std::variant</code>, который будет изучаться позже.
