## 2. Ресурс и проблема ручного освобождения

Ресурс — это нечто, что программа получает, использует, а затем обязана освободить или закрыть.

| Ресурс | Получение | Освобождение |
|---|---|---|
| Динамический массив | `new[]` | `delete[]` |
| Файл C API | `std::fopen` | `std::fclose` |
| Блокировка | `lock` | `unlock` |
| Соединение | открыть | закрыть |

Для каждого ресурса нужно ответить на три вопроса:

1. кто им владеет;
2. когда его нужно освободить;
3. что будет при раннем `return` или исключении.

Рассмотрим ручное управление:

~~~cpp
void process(bool stop_early) {
    int* data = new int[100]{};

    if (stop_early) {
        delete[] data; // эту строку легко забыть
        return;
    }

    perform_operation(); // может выбросить исключение
    delete[] data;
}
~~~

Память не освободится, если исключение передаст управление мимо последней строки. Добавление `delete[]` в каждую ветвь не устраняет причину: корректность по-прежнему зависит от того, не забыл ли программист очередное освобождение.

**Практика:** [01_manual_resource_management.cpp](steps/01_manual_resource_management.cpp).

> [!question] Контрольный вопрос
> Почему одного `delete[]` в конце функции недостаточно?

> [!success]- Ответ
> Не все пути выполнения доходят до конца. Ранний `return` или исключение могут пропустить строку освобождения.

## 3. RAII: ресурс принадлежит объекту

RAII — **Resource Acquisition Is Initialization**, «захват ресурса является инициализацией».

Идея состоит не просто в наличии конструктора и деструктора. Главное — выразить **владение**:

1. конструктор получает ресурс или сообщает о неудаче;
2. полностью созданный объект всегда корректен;
3. деструктор освобождает ресурс;
4. пользователь класса не вызывает освобождение вручную;
5. время жизни ресурса связано с временем жизни объекта.

~~~cpp
class IntArray {
public:
    explicit IntArray(int size)
        : size_(size), data_(nullptr) {
        if (size_ < 0) {
            throw std::invalid_argument("negative size");
        }

        if (size_ > 0) {
            data_ = new int[size_]{};
        }
    }

    ~IntArray() noexcept {
        delete[] data_;
    }

private:
    int size_;
    int* data_;
};
~~~

### 3.1 Инварианты

Инвариант — правило, которое должно быть истинным для каждого наблюдаемого состояния объекта.

Для `IntArray`:

~~~text
size_ >= 0
size_ == 0  ⇒  data_ == nullptr
size_ > 0   ⇒  data_ != nullptr
~~~

Конструктор должен установить эти правила. Каждый публичный метод обязан их сохранить.

### 3.2 Почему копирование пока запрещено

Автоматически созданное копирование скопирует адрес `data_`, а не сам массив. Два объекта попытаются дважды освободить одну память. До изучения глубокого копирования и перемещения операции объявим запрещенными:

~~~cpp
IntArray(const IntArray&) = delete;
IntArray& operator=(const IntArray&) = delete;
~~~

**Практика:** [02_raii_owner.cpp](steps/02_raii_owner.cpp).

### 3.3 RAII в стандартной библиотеке

В обычном проекте не следует повторно реализовывать уже готовые владеющие типы:

| Тип | Чем владеет |
|---|---|
| `std::vector` | Динамическим массивом элементов |
| `std::unique_ptr` | Динамическим объектом при единоличном владении |
| `std::fstream` | Открытым файлом |
| `std::lock_guard` | Захваченной блокировкой |

> [!question] Контрольный вопрос
> Кто вызывает `delete[]`, если функция с локальным `IntArray` завершается ранним `return`?

> [!success]- Ответ
> При выходе из области видимости C++ автоматически вызывает деструктор `IntArray`, а он вызывает `delete[]`.

## 4. Исключения и раскрутка стека

Исключение передаёт информацию об ошибке из места, где продолжать работу нельзя, в место, где ошибку можно обработать:

~~~cpp
try {
    IntArray invalid(-1);
} catch (const std::invalid_argument& error) {
    std::cout << error.what() << '\n';
}
~~~

Стандартные исключения обычно перехватывают по константной ссылке. Так не создаётся лишняя копия и не теряется информация о конкретном типе ошибки.

Когда исключение экстренно покидает функцию в месте своего появления, не доходя до ее конца, C++ уничтожает уже созданные локальные объекты и выходит из активных вызовов функций, пока не найдёт подходящий `catch`. Это называется **раскруткой стека**; английский термин — **stack unwinding**.

~~~text
outer() создаёт outer_marker
    └─ inner() создаёт inner_marker
        └─ throw
        └─ уничтожается inner_marker
    └─ уничтожается outer_marker
catch получает исключение
~~~

Именно это поведение делает RAII устойчивым к исключениям: деструкторы полностью созданных владельцев вызываются автоматически при раскрутке стека.

**Практика:** [03_stack_unwinding.cpp](steps/03_stack_unwinding.cpp).

> [!question] Контрольный вопрос
> В каком порядке уничтожатся `inner_marker` и `outer_marker`?

> [!success]- Ответ
> Сначала `inner_marker`, затем `outer_marker`: объекты уничтожаются при выходе из своих областей видимости в порядке, обратном созданию.

## 5. Исключение во время конструирования

Конструктор не возвращает признак успеха. Если корректный объект создать нельзя, конструктор может выбросить исключение. Так конструктор может заявить о нештатной ситуации при попытке сконструировать объект.

Если конструктор завершился исключением:

- объект не считается созданным;
- выражение создания не передаёт объект вызывающему коду;
- **деструктор самого недостроенного объекта не вызывается**;
- полностью созданные поля-объекты и базовые части уничтожаются;
- уничтожение идёт в обратном порядке.

> [!note] Если объект создавался выражением `new T`
> Память под сам объект, выделенная этим выражением, будет освобождена автоматически, если конструктор `T` выбросит исключение. Это не спасает отдельные сырые ресурсы, полученные внутри конструктора.

### 5.1 Ошибка при создании поля

~~~cpp
class Device {
public:
    Device()
        : first_("first", false),
          second_("second", true) {
        std::cout << "constructor body\n";
    }

    ~Device() noexcept {
        std::cout << "destroy Device\n";
    }

private:
    TraceMember first_;
    TraceMember second_;
};
~~~

`first_` успешно создан. Конструктор `second_` выбрасывает исключение. Поэтому:

1. `second_` не считается созданным;
2. `first_` уничтожается;
3. тело `Device()` не начинается;
4. `~Device()` не вызывается.

### 5.2 Ошибка в теле конструктора

Если оба поля успешно созданы, а исключение вышло из тела `Device()`, сначала уничтожится `second_`, затем `first_`. `~Device()` по-прежнему не вызовется.

### 5.3 Почему два сырых ресурса опасны

~~~cpp
class UnsafePair {
public:
    UnsafePair(int first_size, int second_size)
        : first_(new int[first_size]),
          second_(new int[second_size]) {
    }

    ~UnsafePair() noexcept {
        delete[] second_;
        delete[] first_;
    }

private:
    int* first_;
    int* second_;
};
~~~

Если второй `new[]` выбросит исключение, `UnsafePair` не создастся, его деструктор не вызовется, а память из `first_` будет потеряна.

Безопасная композиция:

~~~cpp
class SafePair {
public:
    SafePair(int first_size, int second_size)
        : first_(first_size), second_(second_size) {
    }

private:
    IntArray first_;
    IntArray second_;
};
~~~

Если `second_` не создастся, уже готовое RAII-поле `first_` будет уничтожено автоматически.

**Практика:** [04_constructor_failure.cpp](steps/04_constructor_failure.cpp).

> [!question] Контрольный вопрос
> Почему деструктор недостроенного `Device` не вызывается, а деструктор уже созданного `first_` вызывается?

> [!success]- Ответ
> `Device` не завершил создание, поэтому его время жизни не началось. `first_` уже был создан полностью, поэтому его нужно уничтожить.

## 6. Гарантии безопасности исключений

Гарантия безопасности исключений отвечает на вопрос:

> Что гарантированно будет наблюдать вызывающий код, если операция не завершилась и выбросила исключение?

Это не «режим компилятора» и не автоматическое свойство любой C++-функции. Гарантия является частью контракта конкретной операции и обеспечивается порядком действий внутри неё.

Не путайте два случая:

| Как завершился вызов | Что описывает контракт |
|---|---|
| Функция вернулась обычно | Постусловие: какой результат получен |
| Из функции вышло исключение | Гарантия безопасности: что осталось истинным, несмотря на ошибку |

Таким образом, гарантия не обещает, что операция всегда будет успешной. Она описывает, насколько аккуратно операция завершится при неудаче.

RAII и гарантии решают разные задачи:

| Вопрос | Что за него отвечает |
|---|---|
| Будут ли освобождены ресурсы? | RAII и деструкторы |
| Останется ли объект корректным? | Как минимум базовая гарантия |
| Изменится ли его состояние? | Базовая или строгая гарантия |
| Может ли операция вообще выбросить? | Невыбрасывающая гарантия |

Гарантии рассматриваются при соблюдении предусловий. Например, вызов `operator[]` с неверным индексом нарушает его предусловие и приводит к неопределённому поведению. Обсуждать «состояние после исключения» здесь нельзя: функция не обещала проверку.

### 6.1 Отсутствие гарантии

Это не уровень безопасности, а отсутствие обещаний. После исключения могут быть:

- нарушены инварианты;
- потеряны ресурсы;
- оставлены висячие указатели;
- объект нельзя безопасно использовать или даже уничтожить.

Такой метод не является безопасным по отношению к исключениям.

### 6.2 Базовая гарантия: объект изменился, но остался корректным

Базовая гарантия обещает:

- инварианты сохранены;
- ресурсы не потеряны;
- объект можно безопасно уничтожить и продолжить использовать;
- конкретные данные могли измениться частично.

Пусть исходное состояние — `[10, 20]`. Метод успевает записать `100` в первый элемент, а затем выбрасывает исключение:

~~~cpp
void update_with_basic_guarantee(
    int new_first,
    int new_second,
    bool fail_after_first
) {
    first_ = new_first;

    if (fail_after_first) {
        throw std::runtime_error("update failed");
    }

    second_ = new_second;
}
~~~

После ошибки состояние равно `[100, 20]`:

- объект не сломан;
- оба значения допустимы;
- ресурсы не потеряны;
- операция выполнена только частично.

Это базовая, а не строгая гарантия.

### 6.3 Строгая гарантия: либо вся операция, либо никакой

Строгая гарантия обещает:

> Если операция выбросила исключение, наблюдаемое состояние объекта останется таким же, как до вызова.

Это часто называют семантикой «фиксации или отката»: **commit or rollback**.

Типичная схема:

~~~text
1. проверить аргументы;
2. подготовить новое состояние отдельно от текущего объекта;
3. выполнить все опасные действия над временным состоянием;
4. если ошибки нет, короткой невыбрасывающей операцией зафиксировать новое состояние.
~~~

В упрощённом примере все рискованные действия идут до изменения полей:

~~~cpp
void update_with_strong_guarantee(
    int new_first,
    int new_second,
    bool must_fail
) {
    if (must_fail) {
        throw std::runtime_error("update failed");
    }

    // Короткая невыбрасывающая стадия фиксации.
    first_ = new_first;
    second_ = new_second;
}
~~~

При исходном `[10, 20]` и ошибке результат остаётся `[10, 20]`. Если ошибки нет, оба значения меняются на `[100, 200]`.

> [!note] Ограничение строгой гарантии
> Внешние эффекты не всегда можно откатить. Например, уже отправленный по сети пакет или напечатанную строку обычно нельзя «отправить назад». Контракт должен точно говорить, какое наблюдаемое состояние он охватывает.

### 6.4 Гарантия не выбрасывания исключения: операция не сообщает об ошибке исключением

Гарантия не выбрасывания исключения, или **no-throw guarantee**, обещает, что операция не выбросит исключение.

Примеры для `IntArray`:

~~~cpp
int size() const noexcept;
bool empty() const noexcept;
void clear() noexcept;
~IntArray() noexcept;
~~~

Важно различать:

- **гарантию** — фактическое поведение кода;
- **`noexcept`** — языковое обещание, что исключение не выйдет наружу.

Одно слово `noexcept` не делает реализацию безопасной. Если из такой функции всё-таки выйдет исключение, оно не превратится в успешный результат: программа завершится через `std::terminate`.

### 6.5 Сравнение гарантий на одном примере

Исходное состояние — `[10, 20]`. Вызывается изменение на `[100, 200]`.

| Контракт | Что может быть после ошибки | Можно ли продолжить работу |
|---|---|---|
| Нет гарантии | Любое состояние, включая сломанный объект | Не обязательно |
| Базовая | Например, `[100, 20]` | Да, объект корректен |
| Строгая | Только исходное `[10, 20]` | Да |
| Невыбрасывающая | Исключения нет; операция завершается по контракту | Да |

Базовая и строгая гарантии описывают именно ветвь с исключением. Строгая гарантия включает базовую: если состояние вообще не изменилось, оно точно осталось корректным. Невыбрасывающая гарантия убирает саму ветвь «из функции вышло исключение».

### 6.6 Как выбирать гарантию

Для каждой публичной операции:

1. сформулируйте предусловия;
2. выпишите действия, способные выбросить исключение;
3. выполните проверки до изменения объекта;
4. если нужен откат, подготовьте новое состояние во временных RAII-объектах;
5. оставьте для стадии фиксации только невыбрасывающие действия;
6. не обещайте более сильную гарантию, чем реально можете обеспечить.

Строгая гарантия обычно удобнее для вызывающего кода, но может требовать дополнительной памяти или копирования. Базовая гарантия не является ошибкой проектирования, если частично изменённое состояние допустимо и задокументировано.

### 6.7 На примере `resize()`, почему для него рекомендуется задать строгую гарантию

Возможный опасный порядок:

~~~text
1. удалить старый массив;
2. попробовать выделить новый.
~~~

Если второй шаг завершится с `std::bad_alloc`, старые данные уже потеряны.

Безопасный порядок:

~~~text
1. проверить новый размер;
2. выделить новый массив во временный указатель;
3. скопировать сохраняемые элементы;
4. только после успеха удалить старый массив;
5. записать новые `data_` и `size_`.
~~~

Для массива `int` после успешного `new[]` оставшаяся подготовка нового состояния не выбрасывает:

- присваивание `int` не выбрасывает;
- `delete[]` для такого массива не выбрасывает;
- запись указателя и размера не выбрасывает.

Поэтому результат имеет вид:

~~~text
new[] не удался
    → исключение
    → старые data_ и size_ не изменены

new[] удался
    → элементы скопированы
    → старый ресурс освобождён
    → новое состояние зафиксировано
~~~

Это строгая гарантия для ошибки выделения памяти.

> [!warning] Обобщённый контейнер сложнее
> Если бы массив хранил не `int`, а объекты с копирующей операцией, способной выбросить исключение, обычного сырого `new_data` было бы недостаточно. Новый ресурс нужно поместить во временный RAII-объект, чтобы он сам освободил память при ошибке копирования.

### 6.8 Какие гарантии дают операции `IntArray`

| Операция | Гарантия | Почему |
|---|---|---|
| `size()`, `empty()` | Невыбрасывающая | Только читают поля `int` |
| `fill()` | Невыбрасывающая | Присваивает `int` существующим элементам |
| `clear()` | Невыбрасывающая | Освобождает массив `int` и восстанавливает пустой инвариант |
| `at()` при неверном индексе | Строгая | Проверка выполняется до изменения |
| `resize()` для ошибки `new[]` | Строгая | Старое состояние не меняется до успешной подготовки нового |
| `operator[]` при неверном индексе | Нет гарантии | Нарушено предусловие функции |

**Практика:** [05_exception_safe_resize.cpp](steps/05_exception_safe_resize.cpp).

> [!question] Контрольные вопросы
> 1. После ошибки объект изменился, но остался корректным. Какая это гарантия?
> 2. В какой момент `resize()` может безопасно удалить старый массив?
> 3. Почему одного `noexcept` недостаточно, чтобы сделать функцию реально невыбрасывающей?

> [!success]- Ответы
> 1. Базовая.
> 2. Только после того, как новая память успешно выделена и все сохраняемые элементы скопированы.
> 3. `noexcept` задаёт контракт, но не устраняет опасные операции. Реализация сама должна быть невыбрасывающей; иначе выход исключения приведёт к `std::terminate`.

## 7. Деструкторы и `noexcept`

### 7.1 Почему деструктор не должен выбрасывать исключений

Во время раскрутки стека уже обрабатывается одно исключение. Если деструктор позволит выбросить второе, программа завершится через `std::terminate`.

Поэтому освобождение ресурса проектируют как `noexcept` операцию, не имеющую права выбрасывать исключения:

~~~cpp
~IntArray() noexcept {
    delete[] data_;
}
~~~

Если операция, завершающая существование объекта способна сообщить об ошибке, для её явной обработки обычно дают отдельный метод вроде `close()`. Деструктор остаётся безопасной резервной операцией.

### 7.2 Спецификатор `noexcept`

~~~cpp
void clear() noexcept;
~~~

Такая запись — обещание: исключение не должно покинуть функцию. `noexcept` не перехватывает и не подавляет исключение. Если оно всё же выйдет наружу, будет вызван `std::terminate`.

Подходят:

~~~cpp
~IntArray() noexcept;
int size() const noexcept;
bool empty() const noexcept;
int& operator[](int index) noexcept;
const int& operator[](int index) const noexcept;
void fill(int value) noexcept;
void clear() noexcept;
~~~

Не подходят:

~~~cpp
explicit IntArray(int size); // проверка и new[]
int& at(int index);          // может выбросить out_of_range
void resize(int new_size);   // проверка и new[]
~~~

`operator[]` может быть `noexcept`, потому что он не проверяет индекс. Корректный индекс является его предусловием. Ошибочный индекс не превращается в исключение — он приводит к неопределённому поведению. Для проверяемого доступа есть `at()`.

### 7.3 Оператор `noexcept(expression)`

Вторая форма проверяет контракт выражения во время компиляции, не выполняя его:

~~~cpp
void safe_operation() noexcept;
void risky_operation();

static_assert(noexcept(safe_operation()));
static_assert(!noexcept(risky_operation()));
~~~

Не путайте:

- `noexcept` после объявления задаёт контракт;
- `noexcept(expression)` вычисляет логическое значение.

**Практика:** [06_noexcept_contracts.cpp](steps/06_noexcept_contracts.cpp).

> [!warning] Не запускайте нарушение `noexcept` вместе с остальными тестами
> Функция `void fail() noexcept { throw ...; }` завершит весь процесс. Для такого эксперимента нужен отдельный запуск.

## 8. Перегрузка операторов

Перегруженный оператор — это функция со специальным именем `operator<знак>`. Она даёт пользовательскому типу привычный синтакс:

~~~cpp
numbers[1] = 42;   // обращение к элементу массива по индексу

if (first == second) {
    std::cout << first << '\n';   // оператор потокового вывода для объекта нашего класса
}
~~~

Перегрузка не создаёт новую возможность, которую нельзя было бы выразить обычным методом. Её цель — сделать интерфейс типа естественным. Оператор стоит добавлять, только если его смысл:

- однозначен для этого типа;
- похож на привычный смысл знака;
- не порождает побочных эффектов, неспецифичных для операции;
- не нарушает инварианты.

Например, `matrix1 + matrix2` выглядит естественно, а `student1 + student2` требует догадываться о смысле.

### 8.1 Количество операндов

**Операнд** — значение, над которым выполняется операция. Например, в `left + right` операндами являются `left` и `right`.

| Вид | Выражение | Операнды |
|---|---|---:|
| Унарный | `-value`, `!value`, `++value` | 1 |
| Бинарный | `left + right`, `left == right` | 2 |
| Вызов | `function(a, b)` | 1 объект и любое допустимое число аргументов |
| Индексация в C++20 | `container[index]` | 1 объект и 1 индекс |

Один знак может иметь несколько форм. Например, `-value` — унарный минус, а `left - right` — бинарный.

### 8.2 Какие операторы можно перегружать

Точный перечень имён операторных функций в C++20:

~~~text
new     delete   new[]   delete[]   co_await   ()    []    ->    ->*
~       !        +       -          *          /     %     ^     &
|       =        +=      -=         *=         /=    %=    ^=    &=
|=      ==       !=      <          >          <=    >=    <=>   &&
||      <<       >>      <<=        >>=        ++    --    ,
~~~

В таблице ниже каждый оператор указан ровно один раз.

| Форма | Операторы | Комментарий |
|---|---|---|
| Только унарная | `~`, `!` | Один операнд |
| Унарная или бинарная | `+`, `-`, `*`, `&` | Например, `-x` и `a - b` |
| Только бинарная | `/`, `%`, `^`, <code>&#124;</code>, `<<`, `>>`, `&&`, <code>&#124;&#124;</code>, `->*` | Два операнда |
| Присваивание | `=`, `+=`, `-=`, `*=`, `/=`, `%=`, `^=`, `&=`, <code>&#124;=</code>, `<<=`, `>>=` | Изменяют левый операнд |
| Сравнение | `==`, `!=`, `<`, `>`, `<=`, `>=`, `<=>` | Равенство и упорядочивание |
| Инкремент и декремент | `++`, `--` | Есть префиксная и постфиксная формы |
| Вызов и доступ | `()`, `[]`, `->` | Имеют особые правила |
| Запятая | `,` | Бинарный оператор с особым синтаксисом |
| Управление памятью | `new`, `new[]`, `delete`, `delete[]` | Специальные правила |
| Корутины | `co_await` | Специальные правила |

`<<` и `>>` для потоков — не отдельные «операторы ввода-вывода». Это те же перегружаемые `<<` и `>>`; их смысл определяют типы операндов.

Функции преобразования, например `explicit operator bool() const`, и пользовательские литералы, например `operator""_suffix`, в этот перечень не входят. Они используют слово `operator`, но объявляются по другим грамматическим правилам.

### 8.3 Что нельзя перегрузить или изменить

Стандарт C++20 прямо указывает, что не перегружаются `.`, `.*`, `::` и `?:`. Символы препроцессора `#` и `##` также нельзя перегружать.

Другие перечисленные ниже конструкции не входят в допустимый грамматикой перечень имён `operator...`, поэтому определить для них свою операторную функцию нельзя:

| Синтаксическая конструкция | Назначение |
|---|---|
| `::` | Разрешение области видимости |
| `.` | Прямой доступ к члену |
| `.*` | Доступ через указатель на член |
| `?:` | Тернарный условный оператор |
| `#`, `##` | Символы препроцессора, а не операторы выражений C++ |
| `sizeof`, `alignof`, `typeid`, `noexcept` | Встроенные операции языка |
| `static_cast`, `dynamic_cast`, `const_cast`, `reinterpret_cast` | Языковые преобразования |

Кроме того, при перегрузке нельзя:

- придумать новый знак, например `**`;
- изменить приоритет: `a + b * c` всегда группируется как `a + (b * c)`;
- изменить ассоциативность: `a = b = c` группируется справа;
- изменить число операндов: бинарному `+` нужны два операнда;
- задать параметры по умолчанию для обычных операторов; `operator()` — особый случай;
- перегрузить оператор только для встроенных типов.

Для обычного унарного или бинарного оператора хотя бы один операнд должен иметь классовый или перечислимый тип:

~~~cpp
Counter operator+(Counter left, int right); // можно
int operator+(int left, int right);          // нельзя
~~~

У функций управления памятью `operator new` и `operator delete` особые сигнатуры и правила; они не описываются этим упрощённым правилом.

### 8.4 Метод или свободная функция

Для оператора-метода левый операнд передаётся неявно как `*this`.

| Выражение | Метод | Свободная функция |
|---|---|---|
| `-value` | `value.operator-()` | `operator-(value)` |
| `left + right` | `left.operator+(right)` | `operator+(left, right)` |
| `++value` | `value.operator++()` | `operator++(value)` |
| `value++` | `value.operator++(0)` | `operator++(value, 0)` |

Оператор-метод для унарного оператора не имеет явных параметров, а для бинарного — имеет один. Свободной функции нужны оба операнда явно.

В C++20 обязаны быть нестатическими методами:

- `operator=`;
- `operator[]`;
- `operator()`;
- `operator->`;
- функции преобразования, например `operator bool()`.

Практическое правило:

- операция изменяет левый объект — часто удобен метод, например `+=`;
- операция симметрична по операндам — часто лучше свободная функция, например `==` и `+`;
- левый операнд имеет чужой тип — нужна свободная функция.

`operator<<` для потока обычно свободен, потому что в `std::cout << value` левый операнд имеет тип `std::ostream`, который мы не можем изменить:

~~~cpp
std::ostream& operator<<(std::ostream& output, const IntArray& array);
~~~

### 8.5 Типичные сигнатуры и возвращаемые типы

| Оператор | Типичная сигнатура | Почему |
|---|---|---|
| Присваивание | `T& operator=(const T& other)` | Цепочка `a = b = c` |
| Составное присваивание | `T& operator+=(const T& right)` | Изменяет и возвращает левый объект |
| Бинарная арифметика | `T operator+(T left, const T& right)` | Создаёт новое значение |
| Унарный минус | `T operator-() const` | Не меняет исходный объект |
| Префиксный `++` | `T& operator++()` | Возвращает уже изменённый объект |
| Постфиксный `++` | `T operator++(int)` | Возвращает копию старого значения |
| Равенство | `bool operator==(const T& left, const T& right)` | Отвечает на вопрос «равны ли?» |
| Индексация | `Element& operator[](Index index)` | Даёт доступ к элементу |
| Константная индексация | `const Element& operator[](Index index) const` | Даёт только чтение |
| Вызов | `Result operator()(Args...) const` | Делает объект вызываемым |
| Потоковый вывод | `std::ostream& operator<<(std::ostream&, const T&)` | Разрешает цепочки вывода |
| Преобразование | `explicit operator bool() const` | У функции нет указанного возвращаемого типа |

`const` после списка параметров и `noexcept` подчиняются тем же правилам, что и у обычных функций. Если оператор не меняет объект, он обычно должен быть `const`. `noexcept` указывают только тогда, когда реализация действительно не выбрасывает.

### 8.6 Составная и обычная арифметика

Сначала реализуйте изменяющую операцию:

~~~cpp
Counter& Counter::operator+=(int delta) noexcept {
    value_ += delta;
    return *this;
}
~~~

Она возвращает `*this` по ссылке, поэтому работают цепочки:

~~~cpp
(counter += 2) += 3;
~~~

Затем выразите через неё создание нового значения:

~~~cpp
Counter operator+(Counter left, int delta) noexcept {
    left += delta;
    return left;
}
~~~

Параметр `left` намеренно принимается по значению: это копия, которую можно изменить. Исходный левый операнд не меняется.

Так основная логика и проверка инвариантов не дублируются. Аналогично строят `-` через `-=`, `*` через `*=` и так далее.

Если операция математически симметрична, полезно поддержать оба порядка:

~~~cpp
Counter operator+(Counter left, int right) noexcept;
Counter operator+(int left, Counter right) noexcept;

Counter a = counter + 5;
Counter b = 5 + counter;
~~~

Метод `Counter::operator+(int)` мог бы реализовать только `counter + 5`: у выражения `5 + counter` слева находится `int`, а не `Counter`.

**Практика:** [07_operator_overloading_basics.cpp](steps/07_operator_overloading_basics.cpp).

### 8.7 Префиксная и постфиксная формы `++` и `--`

~~~cpp
Counter& operator++() noexcept {       // ++counter
    ++value_;
    return *this;
}

Counter operator++(int) noexcept {     // counter++
    Counter old_value(*this);
    ++(*this);
    return old_value;
}
~~~

Параметр `int` в постфиксной версии — фиктивная метка для компилятора. Обычно его не используют и даже не именуют.

Разница наблюдается в результате всего выражения:

~~~cpp
Counter a(5);
Counter first = ++a; // a == 6, first == 6

Counter b(5);
Counter second = b++; // b == 6, second == 5
~~~

Постфиксная форма обычно дороже: ей нужно сохранить старое значение.

### 8.8 Сравнения

Для `IntArray` равенство означает равенство размеров и всех элементов. Адреса `data_` сравнивать нельзя: два независимых объекта могут хранить одинаковые значения в разной памяти.

~~~cpp
bool operator==(const IntArray& left, const IntArray& right) noexcept;
~~~

Для упорядочивания можно определить `<`, `<=`, `>`, `>=`. В C++20 добавлен оператор трёхстороннего сравнения `<=>`. Он может уменьшить дублирование, но требует отдельного разбора категорий сравнения.

В C++20 компилятор может переписать `a != b` через `!(a == b)`, если подходящий `operator==` найден. Явный `operator!=` в учебном примере оставлен, чтобы показать обычную связь между двумя операторами.

### 8.9 Две версии `operator[]`

~~~cpp
int& operator[](int index) noexcept {
    return data_[index];
}

const int& operator[](int index) const noexcept {
    return data_[index];
}
~~~

Неконстантная версия возвращает доступ к настоящему элементу и разрешает запись `array[0] = 10`. Константная версия разрешает только чтение.

~~~cpp
IntArray values(3);
values[0] = 10;

const IntArray& read_only = values;
int first = read_only[0];
// read_only[0] = 20; // ошибка
~~~

Здесь важны оба `const`:

- `const` в `const int&` запрещает менять элемент через возвращённую ссылку;
- `const` после `(int index)` разрешает вызвать метод для `const IntArray`.

Возврат по ссылке нужен, чтобы `array[0] = 10` изменяло настоящий элемент, а не временную копию.

### 8.10 `operator[]` и `at()` имеют разные контракты

- `operator[]` не проверяет границы; корректный индекс — предусловие;
- `at()` проверяет индекс и выбрасывает `std::out_of_range`.

Перегрузка не заставляет `operator[]` выполнять проверку. Его точный контракт определяет автор класса. В `IntArray` выбрана та же модель, что и у `std::vector`: `[]` не проверяет границы, а `at()` проверяет и при ошибке выбрасывает исключение.

### 8.11 Объект как функция: `operator()`

`operator()` создаёт функциональный объект — объект, который можно вызвать как функцию:

~~~cpp
class LinearFunction {
public:
    LinearFunction(double coefficient, double offset) noexcept
        : coefficient_(coefficient), offset_(offset) {
    }

    double operator()(double x) const noexcept {
        return coefficient_ * x + offset_;
    }

private:
    double coefficient_;
    double offset_;
};

LinearFunction line(2.0, 3.0);
double result = line(5.0); // 13.0
~~~

В отличие от обычных унарных и бинарных операторов, `operator()` может иметь несколько параметров и параметры по умолчанию.

### 8.12 Потоковый вывод

`operator<<` возвращает тот же поток по ссылке, чтобы работали цепочки:

~~~cpp
std::cout << "values = " << values << '\n';
~~~

Выражение группируется слева:

~~~text
((std::cout << "values = ") << values) << '\n';
~~~

Каждый `operator<<` получает поток, записывает в него очередное значение и возвращает этот же поток.

### 8.13 Функции преобразования

Преобразование к `bool` выражает вопрос «массив непуст?»:

~~~cpp
explicit operator bool() const noexcept {
    return !empty();
}
~~~

`operator bool` не имеет указанного перед именем возвращаемого типа: целевой тип `bool` уже записан в имени функции.

`explicit` разрешает контекстное преобразование в логическом условии:

~~~cpp
if (values) {
    // Массив непуст.
}
~~~

При этом оно не даёт массиву случайно участвовать в арифметике или неявно преобразовываться в `int`.

### 8.14 Операторы с особыми рисками

Не всё, что можно перегрузить, стоит перегружать.

- `operator&&` и `operator||` не сохраняют короткое замыкание встроенных операторов: оба операнда вычисляются для вызова функции.
- `operator,` даёт неожиданную семантику привычному знаку запятой.
- `operator&` может изменить смысл `&object`, то есть получение адреса.
- `operator new` и `operator delete` управляют выделением и освобождением сырой памяти, а не самими конструктором и деструктором. Это отдельная продвинутая тема.
- `operator->` повторно применяется к результату, пока не будет получен сырой указатель. Его обычно реализуют в умных указателях и прокси-классах.

Для вводной работы достаточно уметь узнавать эти случаи. Перегружать их в `IntArray` не нужно.

### 8.15 Нужен ли `friend`

Свободную функцию можно объявить другом класса, чтобы дать ей доступ к `private`. `friend` не делает функцию методом.

В этой работе `operator==` и `operator<<` можно реализовать через публичные `size()` и `operator[]`, поэтому `friend` им не нужен.

### 8.16 Какие операторы нужны `IntArray`

| Оператор | Роль | Форма |
|---|---|---|
| `operator[]` | Доступ к элементу | Два метода: константный и неконстантный |
| `operator==` | Сравнение содержимого | Свободная функция |
| `operator!=` | Неравенство | Свободная функция через `operator==` |
| `operator<<` | Вывод элементов | Свободная функция |
| `explicit operator bool` | Проверка на непустоту | Константный метод |

Операторы `+`, `-`, `++`, `()` и `->` в `IntArray` не добавляются: для требуемого интерфейса у них нет достаточно естественного смысла.

**Практика:** [08_array_operators.cpp](steps/08_array_operators.cpp).

> [!question] Контрольные вопросы
> 1. Сколько явных параметров у бинарного оператора-метода?
> 2. Почему `5 + counter` нельзя реализовать как метод `Counter`?
> 3. Зачем постфиксному `operator++` фиктивный `int`?
> 4. Почему `operator[]` нужен в константной и неконстантной версиях?
> 5. Почему `operator<<` для `std::cout << array` не делают методом `IntArray`?
> 6. Почему обычно не стоит перегружать `&&` и `||`?

> [!success]- Ответы
> 1. Один: левый операнд уже передан как `*this`.
> 2. Слева находится `int`, поэтому вызвать метод `Counter` у левого операнда нельзя. Нужна свободная функция.
> 3. Он отличает постфиксную форму от префиксной.
> 4. Неконстантная версия разрешает изменение элемента через `int&`. Константная разрешает чтение из `const IntArray`, но возвращает `const int&`.
> 5. Левый операнд имеет тип `std::ostream`, а не `IntArray`.
> 6. Перегруженные версии не сохраняют короткое замыкание: вычисляются оба операнда.

## 9. Итоговое задание IntArray

Заготовка: [01_int_array.cpp](tasks/01_int_array.cpp).

Реализуйте `IntArray`, единолично владеющий динамическим массивом `int`.

### 9.1 Инварианты

~~~text
size_ >= 0
size_ == 0  ⇒  data_ == nullptr
size_ > 0   ⇒  data_ != nullptr
~~~

Они должны выполняться:

- после успешного конструирования;
- после каждого успешного метода;
- после любого перехваченного исключения из метода уже существующего объекта.

### 9.2 Обязательный интерфейс

~~~cpp
class IntArray {
public:
    IntArray() noexcept;
    explicit IntArray(int size);
    ~IntArray() noexcept;

    IntArray(const IntArray&) = delete;
    IntArray& operator=(const IntArray&) = delete;

    int size() const noexcept;
    bool empty() const noexcept;
    explicit operator bool() const noexcept;

    int& operator[](int index) noexcept;
    const int& operator[](int index) const noexcept;

    int& at(int index);
    const int& at(int index) const;

    void fill(int value) noexcept;
    void clear() noexcept;
    void resize(int new_size);

private:
    void validate_index(int index) const;

    int size_;
    int* data_;
};

bool operator==(const IntArray& left, const IntArray& right) noexcept;
bool operator!=(const IntArray& left, const IntArray& right) noexcept;
std::ostream& operator<<(std::ostream& output, const IntArray& array);
~~~

### 9.3 Требуемое поведение

- `IntArray()` создаёт пустой массив и не выбрасывает исключений.
- `IntArray(int)` отклоняет отрицательный размер через `std::invalid_argument`.
- Массив положительного размера заполняется нулями.
- Деструктор освобождает память.
- `operator[]` не проверяет индекс.
- `at()` выбрасывает `std::out_of_range` и не изменяет объект при ошибке.
- `fill()` заполняет все элементы.
- `clear()` можно безопасно вызывать повторно.
- `resize()` сохраняет помещающиеся элементы, добавляет нули и предоставляет строгую гарантию для ошибки выделения.
- `operator==` сравнивает размеры и элементы.
- `operator<<` выводит `[1, 2, 3]` и возвращает поток.
- `explicit operator bool()` сообщает, что массив непуст.

### 9.4 Последовательность реализации

1. Пустой конструктор, `size()`, `empty()` и `operator bool()`.
2. Конструктор с размером и деструктор.
3. Две версии `operator[]`.
4. `validate_index()` и две версии `at()`.
5. `fill()` и повторно безопасный `clear()`.
6. `resize()` с поздним удалением старого ресурса.
7. Сравнение и потоковый вывод как свободные функции.
8. Проверка `noexcept` и запуск санитайзеров.

## 11. Типичные ошибки

| Ошибка | Последствие | Как исправить |
|---|---|---|
| Ручной `delete[]` в `main()` | Владение не инкапсулировано | Освобождать в деструкторе |
| Ожидание деструктора недостроенного объекта | Неверная модель времени жизни | Размещать ресурсы в уже созданных RAII-полях |
| Два сырых `new[]` в одном конструкторе | Утечка при ошибке второго выделения | Композиция RAII-владельцев |
| Удаление старого массива до нового `new[]` | Потеря данных при исключении | Сначала полностью подготовить новое состояние |
| `noexcept` у выделяющей память функции | `std::terminate` при ошибке | Убрать ложное обещание |
| `operator[]` возвращает `int` | `array[0] = value` изменяет временную копию | Вернуть `int&` |
| Нет константного `operator[]` | Нельзя читать из `const IntArray` | Добавить `const int& operator[](int) const` |
| Сравнение `data_` | Сравниваются адреса, а не значения | Сравнить размеры и элементы |
| Неявный `operator bool()` | Нежелательные преобразования | Добавить `explicit` |
| Поверхностное копирование владельца | Двойное освобождение | До следующей темы запретить копирование |
